# インセプションデッキ — マイクラ Mod 開発プロジェクト

> **本ドキュメントの位置付け**: 軽量（簡易）版。プロジェクトの方向性を最低限揃えるため、テンプレート 10 問のうち中核となる 6 問を埋める。残りの 4 問はプロジェクトの状況変化に応じて随時追記する。

---

## 1. なぜやるのか？

個人学習目的で、TDD・XP プラクティス・段階的リリースを「実際に手を動かして体得」する場として、マイクラ Mod 開発を題材にする。座学では身につきにくい「テストで保護しながら動くものを段階的に育てる」感覚を、ゲームというフィードバックの早い領域で得ることが目的。

解決したい問題:

- 業務コードでは試しにくい「最小から段階的に世界を広げる」進め方を、実際の成果物を伴って経験したい。
- AI コーディングエージェント（Claude Code）と協働しながら TDD を回すワークフローを検証したい。
- 受入テストを「実環境で自動実行」する体験を積みたい（モックではなく実 Minecraft 環境）。

---

## 2. どんなビジョンなのか？（エレベーターピッチ）

> **ai-programing-exercise mod**（仮称）は、
> **「TDD と XP プラクティスを体験したい開発者」**向けの、
> **「段階的にワールド要素が増える Minecraft Mod」**である。
> これは **「最小起動 → カスタムブロック → カスタムアイテム → 地形/バイオーム」と段階的にスコープを広げる** ことができ、
> **既存の素のマイクラ Mod 開発と違って**、
> **すべての変更が GameTest による受入テストで保護されている** という特徴がある。

---

## 3. スコープの範囲はどこか？（やる / やらない）

### やる（IN）

- NeoForge 1.21.11 ベースの Mod として動作させる
- `@GameTest` を中核とする受入テスト自動実行ハーネス
- JUnit 5 によるユニットテスト層
- CI（GitHub Actions）から `runGameTestServer` をヘッドレス実行
- カスタムブロック・アイテム・バイオーム等のワールド要素を段階的に追加
- 各ストーリーは TDD（Red → Green → Refactor）で進める

### やらない（OUT）

- マルチプレイ最適化・ネットワーク同期の高度なチューニング
- 他 Mod との互換性検証（Forge 系・Fabric 系）
- 配布物のリリースエンジニアリング（CurseForge 公開等）— 個人学習が目的のため
- ビジュアルの作り込み（テクスチャ・モデル）— 機能成立を優先
- マイクラの細かなバージョン追従（1.21.x 系で固定）

### 後で決める（保留）

- ワールドジェン（バイオーム / 構造物）の規模感
- AI / NPC エンティティの導入有無
- データパック・リソースパックの活用範囲

## 5. 基本的な解決策はどのようなものになるか？

```
+------------------------------------------------------------+
|  Minecraft Client / Dedicated Server (NeoForge 1.21.11)    |
|  ┌──────────────────────────────────────────────────────┐  |
|  │  apps/aipe Mod                                       │  |
|  │  ├─ Mod 本体（ブロック・アイテム・ジェネレーター）   │  |
|  │  ├─ Registry / Config                                │  |
|  │  └─ Domain ロジック（Minecraft 非依存に分離）        │  |
|  └──────────────────────────────────────────────────────┘  |
+------------------------------------------------------------+
       ↑ runClient / runServer        ↑ runGameTestServer
       (手動確認)                      (自動受入テスト)
+-------------------------------+    +-------------------------+
|  src/test (JUnit 5)           |    |  src/test (@GameTest)   |
|  - Domain ロジック単体テスト  |    |  - 実環境受入テスト     |
+-------------------------------+    +-------------------------+
                  ↑                              ↑
                  └──── ./gradlew test ──────────┘
                              ↑
                       GitHub Actions CI
```

ポイント:

- **ロジック層と Minecraft 層を可能な限り分離** することで、JUnit で速く回せる単体テストの面積を広げる。
- **`@GameTest` は実 Minecraft 環境で実行** し、Block/Item/World 操作の受入テストを担う。
- **CI は ubuntu-latest 上で `runGameTestServer`** をヘッドレス実行し、PR 段階で受入テストを回す。

## 6. 主なリスクは何か？

| リスク | 影響 | 対策 |
|--------|------|------|
| GameTest が CI（ヘッドレス）で動かない | 受入テスト自動化が頓挫 | IT-1 で最初に最小サンプルを CI で動かす検証を実施 |
| マイクラ / NeoForge のバージョン更新で API が変わる | 既存テスト・実装が壊れる | バージョン固定（1.21.11）、ベロシティ実績で更新タイミング判断 |
| 個人プロジェクトゆえ計画より興味の方向に流される | 進捗が読めなくなる | 2 週間イテレーションで小さな成功体験を積む。リリース計画を SSOT として更新 |
| GameTest 用の構造ブロック（NBT）作成が学習コスト高 | IT-1 が長引く | 最小（空 1×1×1）構造から開始し、必要に応じて拡張 |
